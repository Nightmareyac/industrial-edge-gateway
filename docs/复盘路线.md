## 环节 2 ｜ 10 分钟 ｜ 入口：谁触发了 OTA

### 看什么

`Core/Src/freertos.c` → `StartMQTTTask()` 里的 `+MQTTSUBRECV` 分支（搜 `upgrade`）

### 关键点（每个都要能解释"为什么"）

```c
ESP_8266_ClearBuf();
ESP8266_SendCmd("AT+MQTTCLEAN=0\r\n", "OK", 1000);   // ①
g_mqtt_online = 0U;
osDelay(500);                                          // ②
```

| 行 | 为什么 |
|---|---|
| ① `MQTTCLEAN` | MQTT 占的就是 link 0，不清理掉，后面 `AT+CIPSTART` 直接回 ERROR 或者不响应（现象：屏幕卡 `ota2`） |
| ② `osDelay(500)` | `OK` 只代表"命令被接受"，底层 TCP 还在收尾。立刻发下一条会偶发 ERROR |
| ③ `g_mqtt_online = 0` | 让 MQTT 状态机知道"现在是 OTA 态，别来抢串口" |

### 自问

- [ ] OTA 是在哪个任务里执行的？（MQTTTask，**同步阻塞**）
- [ ] 阻塞期间 MQTT 保活/补订阅会不会执行？（不会，同一任务被占住 —— 这正是它能独占串口的原因）
- [ ] 失败后为什么要 `ESP8266_Init()` 再回 `WIFI_CONNECTED`？（模块可能停在半连接状态，不重初始化后面所有 AT 都无响应）
- [ ] 如果 OTA 放在 NetworkTask 里会怎样？（NetworkTask 只是空转，能跑，但会丢掉"OTA 期间 MQTT 心跳该停"的语义）

## 环节 3 ｜ 25 分钟 ｜ 传输层：8 个步骤

### 看什么

`Core/Src/esp8266_ota.c` → `ESP8266_HTTP_OTA_Download()` 全文

按代码里的编号 `1.` 到 `8.` 顺序走，**每一步只问两个问题**：

| 步 | 做什么 | 判据（凭什么算成功） | 失败打什么标记 |
|---|---|---|---|
| 1 | `CIPMODE=0` / `CIPCLOSE` / `CIPMUX=0` | 回 `OK` | `ota1:mux` |
| 2 | 擦 80 个扇区 | 无（阻塞执行） | — |
| 3 | `CIPSTART` | 回 **`OK`** | `ota2:模块原文` |
| 4 | 构造 GET | 无 | — |
| 5 | `CIPSEND=<len>` | 回 **`>`** | `ota7:cps` |
| 6 | 灌数据 | 回 **`SEND OK`** | `ota8:snd` |
| 7 | 收 `+IPD` | 攒到 `\r\n\r\n` 且含 ` 200 ` | `ota3/hdr` `o4:` `ota5:size` `ota6:rx` |
| 8 | 写标志 + 重启 | — | — |

### 三个必须能讲透的设计

**① `CIPSTART` 为什么等 `"OK"`，不等 `"CONNECT"`？**
`CONNECT FAIL` 这个字符串里**也含 `CONNECT`**。用它当判据，"连接失败"会被判成"连接成功"。等 `OK` 最干净——失败路径根本不出现 `OK`。

**② 为什么 `CIPSEND` 要等 `'>'`，灌完还要等 `"SEND OK"`？**
- `'>'` = "模块准备好接收数据了"，没拿到说明链路已断或长度非法
- `SEND OK` = "这 N 个字节真的进了 TCP 发送缓冲"，**这是整条链路上唯一能证明数据发出去了的回执**

上一版用透传模式就是因为缺 `SEND OK`，成了黑盒：TCP 明明连上（netstat 有 ESTABLISHED），服务器日志却一个请求都没有，查了五轮才定位。

**③ 为什么擦除放在第 2 步，不放在收到响应头之后？**
接收缓冲 2048 字节，115200 下 **178ms 就填满**；擦一个扇区要几十毫秒。"边收边擦"必然丢字节 → 固件损坏。

### 自问

- [ ] 如果 MQTT 没清干净，`CIPSTART` 会回什么？（`ALREADY CONNECTED` 或 `ERROR`）
- [ ] 为什么擦 80 个扇区（320KB）而不是全擦 960KB？（按需，省 12 秒等待；固件 206KB，留 100KB 余量）
- [ ] `Content-Length` 从哪开始搜？为什么？（从 `hdr_buf` 里搜；命令模式没有回显，不会误命中）
- [ ] 为什么 `total_fw_size` 上限卡 960KB？（APP 分区大小，超了必然写越界）

## 环节 4 ｜ 20 分钟 ｜ 接收解析：流式状态机（本项目最有含量的部分）

### 先搞清楚 `+IPD` 长什么样

```
+IPD,1460:<1460 字节二进制数据>
```

命令模式下，模块把收到的 TCP 数据**加上帧头**再吐给串口。所以：
- 帧头必须剥掉，**绝不能写进 Flash**（否则 bin 里混进 `+IPD,1460:` 字符串，CRC 必挂）
- 一帧可能只到一半，下一轮才补齐

### 看什么

`ESP8266_HTTP_OTA_Download()` 第 7 步的 `RX_SEEK / RX_LEN / RX_DATA` 三段

### 动手画状态转移图（必画）

```
        ┌──────────────────────────────────────┐
        │                                      │
        ▼                                      │
   ┌─────────┐  找到"+IPD,"   ┌─────────┐  遇到':'  ┌─────────┐
   │ RX_SEEK │───────────────▶│ RX_LEN  │──────────▶│ RX_DATA │
   └─────────┘  消费到帧头之后  └─────────┘  长度就绪  └─────────┘
        ▲                           │                  │
        │      遇到非法字符          │                  │ frame_remain -= take
        └───────────────────────────┘                  │
        ▲                                              │
        └──────────── frame_remain == 0 ────────────────┘
```

### 这一版为什么改（核心论证）

**旧写法**：要求整帧到齐才处理

```c
if ((pay_len == 0U) || (n - pay < pay_len)) {
    OTA_Consume(pos);     // ← pos == 0 时这行是空操作
    osDelay(5);
    continue;
}
```

**三种触发条件任意一个命中 = 永久死锁**：
1. 某一帧长度 > 缓冲可用空间
2. 丢 1 个字节，长度字段被解析成巨大值
3. 帧头正好在缓冲头部，`pos == 0`，`OTA_Consume(0)` 什么都不做

**死锁后的连锁反应**（这一段必须背下来）：
```
MCU 不再消费缓冲 → 缓冲定格 2047 字节
  → ESP 模块 UART 侧发不出来
    → 模块停止从 socket 取数
      → TCP 接收窗口归零
        → HTTP 服务器阻塞在 send()
          → 现象：固件只传了 82KB 就完全不动
```

**新写法**：只记 `frame_remain`，缓冲有多少处理多少

**铁律**：`任何分支都必须消费至少 1 字节`。这是防死锁的唯一可靠办法。

### 自问

- [ ] 如果某个 `+IPD` 帧长 4000 字节，新代码会怎样？（正常处理，分多轮消费完；旧代码直接死锁）
- [ ] 丢了一个字节会怎样？（`RX_LEN` 遇到非法字符丢 1 字节回 `RX_SEEK` 重同步；最坏结果是数据错乱 → CRC 拦下 → Bootloader 保旧 APP）
- [ ] 为什么 `hdr_buf` 用 `static`？（放栈上会压 MQTTTask 的 4096 栈，`cmd_buf`+`http_req` 已占 512）
- [ ] `OTA_Consume` 为什么要 `taskENTER_CRITICAL`？（`memmove` 期间中断还在往缓冲尾部写，必须原子）
- [ ] 为什么用 `OTA_BufFind` 不用 `strstr`？（缓冲满 2047 时末尾**没有 `'\0'`**，`strstr` 会越界读到数组外）

### 产出

状态转移图 + 一段"死锁连锁反应"的因果链。**这是本项目最好的面试素材。**

## 环节 5 ｜ 15 分钟 ｜ 落盘与校验

### 看什么

- `Calc_CRC32()`
- `W25Q64_Write_Safe()`
- 第 8 步的标志写入

### 三个硬件/算法细节

**① W25Q64 为什么必须拆页？**
页编程一次最多 256 字节，且**地址在页内回绕**：

```
从 offset 250 开始写 10 字节：
  250..255 写完 → 不会进位到下一页，而是回到本页 0
  → 覆盖掉本页开头刚写的 6 个字节
```

现象是"写入成功但数据错位"，CRC 永远对不上，而且**随机**（取决于每帧起始地址）。所以 `page_remain = 256 - (addr % 256)`。

**② CRC32 为什么用软件实现，不用 F407 硬件 CRC 单元？**
| | STM32 硬件 CRC | 本工程软件实现 |
|---|---|---|
| 多项式 | `0x04C11DB7` | `0xEDB88320` |
| 位序 | **非反射（MSB first）** | **反射（LSB first）** |
| 与 zlib/以太网一致？ | ❌ 不一致 | ✅ 一致 |

两者多项式是同一个数的正反写，但**算出来的结果完全不同**。要和独立 Bootloader 工程逐位对齐，软件实现最稳。

**③ 为什么 CRC 要"逐块累加"？**
固件是流式接收的，不可能攒够 206KB 再算。CRC 天然支持分段续算：`crc = f(crc, data, len)`，来一块算一块，数学等价。

### 自问

- [ ] 标志四个字段各自不可替代的作用？（magic 判有效 / size 算擦多少 / crc 防写坏 / version 给人看）
- [ ] 为什么先擦标志扇区再写？（避免"新 size + 旧 crc"的半新半旧标志）
- [ ] 写完为什么 `osDelay(1000)` 才复位？（W25Q64 内部 tW 最大 3ms + 状态机收尾，复位太快标志可能还没落盘）
- [ ] `W25Q64_Write` 忙等期间 UART 会丢字节吗？（会，所以擦除要提前做完、接收缓冲要够大）

## 环节 6 ｜ 20 分钟 ｜ Bootloader 侧（另一份工程）

### 看什么

`D:\A_Myrepo\OTA_BootaLoader\Core\Src\main.c`

| 函数 | 核心逻辑 |
|---|---|
| `App_Image_Is_Valid()` | 三重校验：初始 SP → Reset 向量 → CRC32 |
| `Erase_App_Sectors()` | 按 `fw_size` 动态算要擦几个扇区 |
| `Copy_Image_To_App()` | 逐块搬运，检查 `HAL_FLASH_Program` 返回值，尾字补 `0xFF`，4 字节对齐 |
| `Verify_App_Flash()` | 搬完**回读重算 CRC** 再比一次 |
| `Jump_To_App()` | 清 NVIC → 设 MSP → 设 VTOR → 跳 Reset_Handler |

### 三重校验的判据（要能背）

| 检查 | 判据 | 防什么 |
|---|---|---|
| 初始 SP | 落在 `0x20000000` 段（掩码 `0x2FFE0000`） | 跳到无效栈 → HardFault |
| Reset 向量 | 落在 APP 区 `[0x08010000, +size)` 且 **bit0=1** | 跳到 Bootloader 自己（白屏根因） |
| CRC32 | 与标志里的值一致 | 传输损坏 / 搬运写坏 |

**bit0=1 是为什么？** Cortex-M 的跳转地址必须是 Thumb 地址（最低位 1）。取出来当函数指针用之前要 `& ~1`，但**校验时必须要求它是 1** —— 否则说明这个值根本不是合法的 Thumb 向量。

### 自问

- [ ] 校验失败时怎么处理？（不擦、不搬、清标志、跳旧 APP —— **可恢复性优先**）
- [ ] 为什么跳转前要清 NVIC？（APP 里没初始化的中断，如果还处于 pending 状态，一开中断就跳到野向量）
- [ ] `__set_MSP` 和 `SCB->VTOR` 的先后顺序？（先 MSP 后 VTOR，中间插 `__DSB()` `__ISB()`）
- [ ] 如果 CRC 校验失败但标志已清，下次上电会怎样？（正常跳旧 APP，不会反复重试）

### 产出

一句话：**"Bootloader 的唯一职责是'要么把新固件完整搬过去，要么什么都不做'。"**

## 附：三分钟项目口述稿（背这个）

> 我做的是一个 STM32F407 的工业边缘网关，核心是**巴法云 MQTT 远程 OTA**。
>
> 硬件上 STM32F407 + FreeRTOS + LVGL，联网用 ESP-01S，固件暂存在外挂的 W25Q64 上。
>
> 升级链路是：云端下发 `upgrade` → MQTT 任务收到后清掉 MQTT 连接、把串口让给 HTTP → 用 AT 指令建 TCP、`CIPSEND` 发 GET → 按 `+IPD` 帧解析响应，边收边写 W25Q64 并累加 CRC32 → 收完写一个 OTA 标志 → 重启进 Bootloader。
>
> Bootloader 做三重校验：初始 SP、Reset 向量是否落在 APP 区且是 Thumb 地址、CRC32 是否一致。任何一项不过就**不擦不搬、保留旧 APP**，所以永远不会变砖。
>
> 过程中最难的不是写代码，是**建立可观测性**。最典型的一次：TCP 每次都连上了（netstat 能看到 ESTABLISHED），但服务端日志里一个请求都没有。我用四步把它夹死——netstat 看连接在不在、服务端日志看请求有没有、进程 IO 计数看字节发了多少、屏幕分级标记看设备卡哪一步。最后定位到透传模式没有中间回执，换成命令模式后 `SEND OK` 一出现，问题立刻现形。
>
> 后面又踩了一个更隐蔽的：命令模式传到 82KB 死住。原因是接收解析写成了"整帧到齐才处理"，一旦某一帧超过缓冲或者丢一个字节，就会走进一个"消费 0 字节还 continue"的分支，永久死锁。改成流式状态机，只记剩余长度，边收边写，才彻底解决。
>
> 我的结论是：**流式协议解析里，任何分支都必须保证推进**；**没有回执的链路等于黑盒**。
